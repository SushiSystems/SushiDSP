# Documentation style guide

[`CONTRIBUTING.md`](CONTRIBUTING.md) says what a change must document. This page says how: the
shape every document in this tree already follows.

## Where a document goes

```
README.md                        the front door
CLAUDE.md                        agent operating rules
docs/
  README.md                      the manual index
  CONTRIBUTING.md
  DOCUMENTATION_STYLE_GUIDE.md
  getting_started/                a newcomer's first read, before the architecture chapters
  architecture/                   how the layers fit together as the tree stands today
  modules/                        the index of every module's own README.md, nothing more
  guides/                         task-oriented how-to pages (e.g. the CLI)
  design/                        live intent — a document with at least one open phase
  reference/
    CHANGELOG.md                 what changed and when, by roadmap phase
    KNOWN_ISSUES.md             measured defects left open on purpose
    GLOSSARY.md
    spice/                       the SPICE reference corpus
  api/                           hand-written Doxygen landing page
  api-site/                      generated by `sd doxygen`, never hand-edited
  superpowers/
    specs/                       one design specification per sub-project
    plans/                       one implementation plan per sub-project, a `- [ ]` TDD checklist
  agent/                         everything an agent writes while executing a task
  archive/                       frozen history — added to, never edited
include/SushiDSP/…, modules/<name>/, tools/<name>/, assets/<name>/
                                  each carries its own README.md beside the code
```

### The placement rule

A fact about one module (what it owns, which class does what, where it deviates from the
design spec) goes in that module's own `README.md` — `modules/nodes/tubescreamer/README.md`,
`modules/nodes/room/README.md`, and so on — and nowhere else. `docs/README.md` links to it and
states no fact of its own.

Everything else follows the design spec's status:

- A document describing intent with at least one phase not built lives in `docs/design/`.
  `docs/design/sushidsp.md` and `docs/design/gui_ux_redesign.md` are both design documents
  that describe work not yet in the tree. Read one as a record of intent, never as a
  description of the tree as it stands.
- `docs/design/REMAINING_WORK.md` is the single backlog: every open item, in the order it
  should be taken, with measured-and-accepted defects left to `KNOWN_ISSUES.md` instead of
  repeated there.
- A document that records what an agent did while executing a task (a spec, a plan, a report)
  goes under `docs/agent/` or `docs/superpowers/`.
- Work with nothing left open belongs in `docs/archive/`, frozen: added to, never edited.
- Otherwise, if it describes the tree as it is today, it belongs in the manual proper, sorted
  by what a reader is asking: a newcomer's first orientation goes in `getting_started/`, how
  the layers fit together goes in `architecture/`, a task-oriented walkthrough (running the
  CLI, say) goes in `guides/`, "what is this called or what changed" goes in `reference/`, and
  the index of every module's own `README.md` lives in `modules/README.md` rather than
  repeating each module's facts there.

## The index-entry format

`docs/README.md` links to every document in the tree through one repeated shape:

```markdown
- **[Title](path/to/file.md)** — one sentence saying what the document covers and, where it
  matters, what state it's in (open phase, historical record, generated output).
```

The bold link carries the title. The description after it says why a reader would open the
document, not what it contains line by line. A document with more to say about its own scope
than fits an index entry says so at its own top, not in the index.

## Design-doc status lines

Every document under `docs/design/` opens with a status line stating whether the work it
describes is done:

```markdown
**Status:** Design — open phase, nothing implemented yet.
```

```markdown
**Status:** open, last revised 2026-09-10.
```

A status line that says "design only" or names an open phase means the document describes
intent, not the tree as it stands. Read it as a spec to build from, never as a report of what
exists. `docs/design/sushidsp.md`'s own header states this for the whole design spec: it is
what an implementer builds from, and it may describe a module, a class or a behavior that has
not been written yet.

## Changelog entries

`docs/reference/CHANGELOG.md` is grouped by roadmap phase (design spec §9), each phase citing
its spec and plan under `docs/superpowers/`. Every entry is one line:

```markdown
- 2026-09-08 — Added `AirAbsorption`, ISO 9613-1 at 20 °C and 50 % RH (`AirAbsorption.hpp`, `AirAbsorption.cpp`).
```

The date, a past-tense verb, what changed, and the touched files in backticks. Never the
reason; the reason belongs in the design document the entry may cite. At most 240 characters,
one sentence, no nested bullet. An entry that reads as a paragraph explaining *why* belongs in
the design document instead, however useful the explanation is.

## Doxygen comments

`CONTRIBUTING.md` §3 sets the rule this tree's headers already follow: `@brief`/`@param`/
`@return` on every public function, and no comment beyond that unless the *why* is
non-obvious, because a well-named identifier already says *what* it does. `sd doxygen` builds
`docs/api-site/html/` from these comments starting at `docs/api/mainpage.md`. It documents what
the headers say, is never a substitute for the design spec's reasoning, and is never
hand-edited.

## Voice

Write the way `docs/README.md` and `docs/CONTRIBUTING.md` already do:

- **Declarative and specific.** Name the class, the file, the figure. "`DkCircuit` holds the
  trapezoidal discretisation" beats "the circuit layer handles discretisation".
- **Honest about gaps.** A deferred decision is written down with the reason, not silently
  dropped. `CONTRIBUTING.md` §2 points to the WDF adaptor-tree deferral as the pattern.
- **No marketing language.**
- **Present tense for the tree as it stands**; a design document is the one place future tense
  belongs, because it is describing what does not exist yet.
- **Explain *why*, never *what*,** in both commit messages and source comments. The diff or
  the code already says what changed.

## Prose review

Every piece of prose this tree produces (a manual page, a design document, a commit message,
an agent report) goes through the `humanizer` skill before it is committed, in the language it
is written in. This guide was.

## Links and paths

A path cited in prose is a real path in the tree, spelled exactly as the tree spells it.
Verify it before writing it down, the same discipline `docs/README.md`'s own entries hold to
when they cite a header, a module or a tool script. A link is relative to the file that
carries it, never a URL to a hosting site.
