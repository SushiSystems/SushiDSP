# DD-3 Delay and SPX90 Reverb — Design

Status: approved 2026-09-05 (brainstorm with the user; approaches A1 + B1 chosen).
Research inputs: `docs/reference/research/2026-08-26-boss-dd3-design-dossier.md`,
`docs/reference/research/2026-08-26-yamaha-spx90-design-dossier.md`.

## Scope and targets

Two effect units, modelled from published data only (no hardware on the bench):

- **Boss DD-3, long-chip revision (1986–89)** — electrically a DD-2. One `IAudioNode`,
  1 in / 1 out. The direct/wet mix stays inside the node, as the pedal's LEVEL pot does.
- **Yamaha SPX90** — one `IAudioNode`, 1 in / 2 out. All 30 factory programs, in two tiers:
  the eight reverb/ER programs (Rev1–Rev4, ER1, ER2, Gate, Reverse) calibrate against the
  Surefyre IR pack with null targets; the remaining 22 are functional reconstructions on the
  same engine, documented as uncalibrated.

Claim discipline: the two tiers are stated wherever the programs are listed. A program outside
the calibrated eight never carries a null number.

## Prerequisites owned by other tracks

- **RigGraph per-node multi-channel (finding C1 of the 2026-08-26 DAG review).** The SPX90
  node declares `ports() == {1, 2}`; today `RigGraph::process()` hands every node a 1-element
  output array, so graph integration waits for C1. Until then the node runs under the test
  harness and the direct device path. C2 (unvalidated handles), C3 (pool exhaustion) and
  I1 (MixerNode without delay compensation — the wet/dry comb) are part of the same
  prerequisite set. The user owns this work.
- **Tail preservation across rebuilds.** `RigController::rebuild_and_publish()` rebuilds the
  graph on any structural edit and discards node state; a half-second reverb tail makes that
  cut audible. Needs state migration or a crossfade in the slot. Recorded here; not this
  track's work.

Neither prerequisite blocks the DSP itself: both nodes are built and validated standalone.

## New shared brick: `math/Resampler`

`include/SushiDSP/math/Resampler.hpp` — arbitrary-ratio polyphase resampler.

- Fixed ratio set at `prepare(source_rate, target_rate, max_block)`; all buffers allocated
  there; `process()` is allocation-, lock-, syscall- and throw-free.
- Both units consume it: SPX90 at 48000/31250 (ratio 1.536) both ways, DD-3 at 48000/fs(t)
  where fs(t) moves at control rate. For the DD-3 the ratio changes per block, so the design
  is a polyphase interpolator over a fixed prototype filter with a fractional phase
  accumulator, not a bank rebuilt per ratio.
- Group delay is fixed by the prototype filter and reported through `latency_samples()`.
  This delay puts a floor under the DD-3's minimum delay setting; the spec accepts the floor
  and the plan states the number once the prototype is designed.
- `math/Oversampler` (2x halfband) is untouched; the two solve different problems.

## DD-3 — variable-rate loop (approach A1)

The block chain transcribes the schematic's signal path; the delay-time control moves the
sample clock, not the buffer length. This is the only faithful source of the pedal's
behaviour: pitch slur when the time knob moves, brighter repeats at short settings, darker at
long ones.

```
input ── 6th-order Sallen–Key anti-alias LPF (7 kHz; Q 0.66 / 1.90 / 4.52)
      ── NE570 compressor (open-loop envelope, tau = 6.8 ms)
      ── pre-emphasis
      ── Resampler 48k -> fs(t)
      ── 12-bit quantiser (shared R-2R SAR/DAC character)
      ── fixed-length ring: N = 1024 / 4096 / 16384 by mode switch
      ── Resampler fs(t) -> 48k
      ── NE570 expander ── de-emphasis
      ── 4th-order reconstruction LPF (Q 0.75 / 3.37)
      ── level/mix with direct path
```

- **Feedback** closes around the whole chain in the analog domain, as on the board: the
  repeat signal re-enters before the anti-alias filter and is re-companded and re-quantised
  every pass. Repeat degradation is therefore emergent, not painted on.
- **fs(t)**: the VCO runs 20–82.5 kHz; the time pot reaches it through the R56 (22 kOhm) /
  C52 (0.027 uF) single pole, which is the slew that makes time changes glide. Delay time is
  N / fs; the three N values give the three mode ranges (12.5–50, 50–200, 200–800 ms).
- **HOLD** is a write inhibit on the ring, nothing else.
- The linear analog blocks are `Biquad` cascades with component-derived coefficients; the
  compander is an envelope-driven gain pair with the NE570 time constant; the quantiser is a
  static 12-bit characteristic at the variable rate. The D6b DK core is not used: no block
  here is a nonlinear network that needs a Newton solve, and the dossier's measurements bind
  behaviour, not netlists. (`docs/reference/research/2026-08-26-boss-dd3-design-dossier.md`
  §4 is the topology source.)
- Parameters: TIME, FEEDBACK, LEVEL, MODE (I/II/III + HOLD), all through
  `SmoothedParameter`; MODE changes swap N and clear the ring.

### Model corrections (DR2, 2026-09-05)

Task 2.1 built the four linear networks and found that the schematic's capacitor values, read
through the textbook relations, contradict the pedal's published response. Two corrections ship
in `modules/dd3/include/SushiDSP/dd3/Dd3AnalogFilters.hpp`, and they are recorded here because
the constants do not explain themselves.

#### The unity-buffer Q overshoots the published window

Every section is an equal-R Sallen–Key, so `f0 = 1/(2*pi*R*sqrt(C1*C2))` and, for a buffer of
gain exactly 1, `Q = 0.5*sqrt(C1/C2)`. The dossier's values (§1.3) give the anti-alias sections
Q of 0.6597, 1.9018 and 4.5227, and those three cascade to **+6.449 dB at 7 kHz** — against a
published delay-path response of 40 Hz–7 kHz within +1/−3 dB (dossier §3).

Solving the same network with a buffer of gain K moves Q and leaves f0 alone:

```
H(s) = K / (1 + s*R*(2*C2 + (1-K)*C1) + s^2*R^2*C1*C2)
w0   = 1/(R*sqrt(C1*C2))                       unchanged by K
1/Q  = 1/Q0 + 2*(1-K)*Q0                       Q0 = 0.5*sqrt(C1/C2)
```

The correction bites hardest where Q0 is largest, which is where the peak comes from:

| Section | Q0 (buffer gain 1) | Q at K = 0.9548116 |
| --- | --- | --- |
| AA 1 (Q3) | 0.6596856715 | 0.6347216596 |
| AA 2 (Q4) | 1.9018468068 | 1.4333063892 |
| AA 3 (Q6) | 4.5226701687 | 1.5876726071 |
| RC 1 (Q10) | 0.7500000000 | 0.7137168140 |
| RC 2 (Q9) | 3.3665016461 | 1.6630691464 |

Every corner frequency stays exactly as the components give it.

#### K is fitted to the published window, and it is not a voltage gain

The published window bounds K rather than fixing it. Applied to the delay path (anti-alias into
reconstruction, which is what the published figure measures), K below **0.9431071** puts 7 kHz
past −3 dB and K above **0.9665162** puts the passband peak past +1 dB. `kEmitterFollowerGain`
takes the midpoint, **0.9548116**, so neither limit is approached.

The window is a knife edge in K, which is why the bound is tight enough to be useful. Measured
on the delay path at a 48 kHz rate:

| K | delay path at 7 kHz | delay path passband peak |
| --- | --- | --- |
| 0.9431071 | −2.990 dB | +0.170 dB |
| 0.9548116 | −1.206 dB | +0.354 dB |
| 0.9665162 | +0.736 dB | +1.013 dB |
| 0.98 | +3.175 dB | +3.175 dB |
| 1.0 | +7.081 dB | +7.081 dB |

**K is an effective damping factor, not the emitter follower's loaded voltage gain.** That gain
is around 0.987: a 2SC732 on a 10 kOhm emitter load at half of 9 V draws about 380 µA, so
re ≈ 68 Ohm, and against a 5–10 kOhm load that is K = 0.987 to 0.993. Reaching 0.955 would need
I_E ≈ 80 µA. The constant therefore absorbs the follower's output impedance, its base-current
loading of the shunt capacitor, and whatever the capacitor values are actually mis-read by; the
name records where the dominant term comes from, not a measured device parameter. A swept sine
through a real unit's DIRECT/MONO wet-only path (dossier §4.7 item 1) would replace the fit:
two points, 5 kHz and 7 kHz, solve for K exactly.

Because K is a damping factor and not a gain, the per-section DC loss `K^n` is deliberately not
carried; `Biquad::set_low_pass` gives each section unity gain at DC, which is what ships. A real
follower cascade at K ≈ 0.987 loses 0.34 dB across the three anti-alias sections and 0.57 dB
across all five. That is a level question, and it belongs with the check-point ladder in the
DD-3 node's LEVEL calibration, not in the filter coefficients.

#### One prewarp anchor for the whole cascade

`Biquad::set_low_pass` is the bilinear transform with the corner prewarped at that section's own
f0, so each section gets its own frequency-axis warp and the cascade's composite shape drifts
with the sample rate. `prewarped_corner_hz` instead hands `set_low_pass` a digital corner `fd`
satisfying `tan(pi*fd/fs) = f0 * tan(pi*7000/fs) / 7000` for every section. All sections then
share one warp scale, the cascade is the exact bilinear image of the analogue prototype under a
single monotone frequency map, and the map is exact at 7 kHz.

Per-section prewarp does not by itself leave the published window. It costs rate-invariance and
margin, measured at 7 kHz relative to 1 kHz:

| Chain | prewarp | 48 kHz | 96 kHz | 192 kHz | spread |
| --- | --- | --- | --- | --- | --- |
| anti-alias | per-section | −2.113 dB | −1.455 dB | −1.313 dB | 0.800 dB |
| anti-alias | anchored | −1.259 dB | −1.265 dB | −1.267 dB | 0.009 dB |
| delay path | per-section | −2.634 dB | −1.555 dB | −1.295 dB | 1.339 dB |
| delay path | anchored | −1.206 dB | −1.208 dB | −1.210 dB | 0.005 dB |

A model whose response moves 1.34 dB when the host changes sample rate is not a model of one
pedal. The anchor also buys margin: at a 48 kHz rate the delay path sits 0.366 dB from the −3 dB
limit under per-section prewarp and 1.794 dB from it under the anchor.

The anchor is a constant, 7 kHz, and it assumes the filters run well above 14 kHz. These classes
run at the host rate, 48 or 96 kHz; they are not the ones that follow the DD-3's 20–82.5 kHz
internal clock.

#### The F.BACK take-off sits after de-emphasis, at the wet leg's output

Dossier §1.6 leaves the take-off unresolved: on the scan the expander-output wire at R41 and the
Q9 emitter wire run within 0.4 mm of each other, and §5 open question 1 records the
post-reconstruction reading as an inference at confidence C, not as something read off the board.
Task 2.5 built the loop both ways and measured each. The take-off ships **at the wet leg's
output**, after the reconstruction filter and after de-emphasis, feeding F.BACK and E.LEVEL from
one node.

Reading (a), the take-off before de-emphasis, puts pre-emphasis inside the loop with nothing to
undo it. The forward gain from the pre-emphasis summing node back to the take-off is then

```
kInputPathGainToCheckPointOne * |pre-emphasis| * |anti-alias| * kExpanderOutputStageGain * |reconstruction|
```

which is 20.09 at 100 Hz, 37.69 at 1 kHz and peaks at 100.51 at 5804 Hz. Two consequences follow,
and the pedal contradicts both. The loop passes unity gain at F.BACK 0.011, so the node
regenerates across almost the whole knob: driven with a 10 ms 3 kHz burst at mode S, the second
echo already carries 1.05 times the first echo's energy at F.BACK 0.05, 1.80 at 0.3 and 1.94 at
0.7, and the output reaches 4.49 full scale. And each pass adds the emphasis shelf's +11 dB at
6 kHz, so the repeats brighten, against dossier §3's cumulative darkening. Holding that loop
stable needed a fitted attenuator of 1/100.511 whose value came from nothing on the board.

Reading (b) puts the emphasis pair inside the loop together. Because `set_first_order_shelf`
prewarps the shelf's zero and pole independently, the pair cancels to `|H_pre * H_de| =
1.000000000` at every frequency and at 48, 96 and 192 kHz alike, so what remains is the filters
and the compander:

```
kInputPathGainToCheckPointOne * kExpanderOutputStageGain * |anti-alias| * |reconstruction|
```

| Frequency | Reading (a) | Reading (b) |
| --- | --- | --- |
| 100 Hz | 20.09 | 28.22 |
| 1 kHz | 37.69 | 28.53 |
| 3 kHz | 81.43 | 29.69 |
| 6 kHz | 100.37 | 27.97 |
| 10 kHz | 12.25 | 3.13 |
| peak | 100.51 at 5804 Hz | **29.719044 at 3278 Hz** |

Reading (b) is flat to within 0.4 dB across the passband and then falls with the cascades, which
is the shape the board's own filters give. Its peak is the same number at 48, 96 and 192 kHz, so
the trim that sets `kMaximumFeedback = 1.1` to mean a loop gain of 1.1 is one exact constant
rather than a rate-dependent fit. `kFeedbackPathGain` is therefore
`kFeedbackMixRatio * kFeedbackResidualTrim`: `kFeedbackMixRatio = 33/50` is R12 over VR2 at the
top of the F.BACK pot, and `kFeedbackResidualTrim = 1/19.614569` is what the resistors do not
account for. That residual is dominated by two constants that recirculate through the summing
node under this block order: `kInputPathGainToCheckPointOne` at 4.70358 and
`kExpanderOutputStageGain` at 6.0.

The repeats then behave. Driven with a 10 ms burst of eight equal tones from 400 Hz to 8.1 kHz at
mode S and F.BACK 0.7, the third echo's spectral centroid is 2166 Hz against the first echo's
2462 Hz, and its RMS is 1.05e-2 against 3.65e-2. Across the knob, with the tail measured one to
two seconds after a 3 kHz burst:

| F.BACK | second echo RMS | tail RMS at 1–2 s |
| --- | --- | --- |
| 0.3 | 4.230e-3 | 0 |
| 0.5 | 7.940e-3 | 0 |
| 0.7 | 1.198e-2 | 1.27e-9 |
| 0.9 | 1.551e-2 | 5.93e-3 |
| 1.0 | 1.701e-2 | 3.80e-2 |

Nothing here reads the board, so nothing here closes dossier §5 open question 1. It rules on
which inference the model carries and says why. Dossier §4.7 item 5, an F.BACK sweep to and past
self-oscillation on a real unit, settles the reading for good: reading (a) puts the oscillation
threshold at F.BACK 0.011 with the loop's gain peak at 5804 Hz, reading (b) puts the threshold at
the top of the knob and oscillates at a measured 2973 Hz at mode S, and one sweep separates them.

## SPX90 — structural fixed-point model (approach B1)

One engine, thirty parameter sets.

- **Internal rate and word widths**: 31.25 kHz, 16-bit at the converter boundary, 24-bit
  delay-RAM word, matching the service manual. The arithmetic inside the engine is integer
  (32-bit accumulators standing in for the bit-exact microcode we cannot dump); the fixed
  word widths at the RAM and converter boundaries are what shape the noise floor, so those
  two truncations are modelled exactly.
- **Converter character**: one SAR converter multiplexed across channels with a PCM54HP
  ladder; modelled as shared-quantiser timing and a static 16-bit characteristic.
- **Program core** follows US 4,803,731: clustered early-reflection taps, a delay multiplier,
  and a per-tap low-pass. ROOM SIZE scales tap times structurally (the taps move); LIVENESS
  scales the recirculation gain. This is why approach B2 (generic FDN plus "colour") was
  rejected: it could pass an IR null at one setting and still get the parameter behaviour
  wrong.
- **Program table**: each of the 30 programs is a row of engine parameters
  (tap sets, multipliers, filter settings, output routing), not a separate code path.
  Tier one (the eight) get their rows tuned against the IR pack; tier two rows come from the
  panel parameter ranges in the manual and are labelled uncalibrated in the table itself.
- Output is stereo from the tap routing, as on the unit; input is mono.

## Testing and acceptance

Everything runs through `tests/measure/` and the golden-file conventions from D6a.

| Check | Target |
| --- | --- |
| DD-3 fs(t) vs time setting, all three modes | within 2 % of 20–82.5 kHz / 12.5–800 ms published curve |
| DD-3 AA + reconstruction filter responses | analytic goldens from component values |
| DD-3 compander static curve and tau | NE570 datasheet curve; tau 6.8 ms measured by envelope step |
| DD-3 pitch slur | frequency trace under a time-knob sweep shows the R56/C52 glide, not a jump |
| SPX90 calibrated eight | IR null <= -40 dB against the Surefyre pack (not -60: the pack's capture chain is undocumented, and that ceiling is recorded here as the reason) |
| SPX90 tier two | structural asserts only, e.g. RT60 monotone in ROOM SIZE, ER density monotone in LIVENESS |
| Both nodes | RT traps on `process()`; 0 NaN under the D6b stimulus battery; latency reported and asserted |
| Benchmarks | DD-3 <= 0.15 ms, SPX90 <= 0.35 ms per 256-frame block at 48 kHz (binding) |

## Risks

| Risk | Standing |

| Surefyre IR pack licence and provenance | Verify before committing any derived data; nulls can run against local files if redistribution is unclear. |
