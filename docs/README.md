# SushiDSP documentation

The manual's index. Start at the root [`README.md`](../README.md) if you haven't; this is for
once you're in the tree and need a specific document.

## Where to go

- **[Getting started](getting_started/INTRODUCTION.md)** — what SushiDSP is, the rig graph it
  builds around, and how to set up a workspace to build against it.
- **[Design](design/sushidsp.md)** — the architecture, the math, the SOLID rationale, and the
  product roadmap (D0–D7). This is the authoritative spec an implementer builds from; it
  describes intent and may describe work that does not exist in the tree yet.
- **[Architecture](architecture/README.md)** — how the tree's layers fit together as built
  today, distinct from the design spec's intent; points to `OVERVIEW.md` and to this page's
  module list.
- **[GUI/UX redesign](design/gui_ux_redesign.md)** — the host app's main-window layout,
  audio device panel centering, splitter/mixer automation, cabinet component, and
  mini-DAW panel (Phase 1, implemented). Phase 2 (§10-§19) redesigns the workspace into
  one resizable rig editor, turns the splitter picker into a whole-chain topology choice,
  and adds a gear-browser grid view (Phase 2, implemented except the Pitch field; open items
  in `design/REMAINING_WORK.md`'s Host section).
- **[Contributing](CONTRIBUTING.md)** — the conventions every change is held to: C++17, Allman
  braces, the license header format, the test/CTest-label layout, and how to build (`sd`, never
  `cmake` directly).
- **[Documentation style guide](DOCUMENTATION_STYLE_GUIDE.md)** — how a document is shaped: where
  it goes, and the form every page in this tree already follows.
- **[Command line interface](guides/COMMAND_LINE_INTERFACE.md)** — the `sd` CLI's six
  subcommands (`configure`, `build`, `test`, `doxygen`, …) and how each picks a compiler.
- **[Remaining work](design/REMAINING_WORK.md)** — the single backlog: what is open, in
  the order it should be taken, with the measured defects left to `KNOWN_ISSUES.md`.
- **[Changelog](reference/CHANGELOG.md)** — what changed and when, by roadmap phase.
- **[Known issues](reference/KNOWN_ISSUES.md)** — measured defects left open on purpose, each
  with its figure, its mechanism, the skipped test that documents it, and what closes it.
- **[Glossary](reference/GLOSSARY.md)** — the words this tree fixes a narrower meaning for: bar,
  beat, clip, lane, take, timeline frame and playback speed.
- **[Code of Conduct](CODE_OF_CONDUCT.md)** and **[Security Policy](SECURITY.md)**.
- **[Archive](archive/README.md)** — closed-out design documents, moved here intact once nothing
  in them is still open; currently empty, since SushiDSP hasn't closed one out yet.
- **[Modules index](modules/README.md)** — every module, one line each, linking to its own
  `README.md` for which class owns which block and where it departs from the design spec.
- **[`docs/reference/spice/`](reference/spice/)** — the SPICE reference corpus: netlist-directive
  `.asc` files and Koren/Norman `.sub` models for each circuit block, exported to CSV by
  `tools/spice/export.py` and read back by `tests/measure/SpiceCsv.hpp`. Populating it needs
  LTspice, which is a user-side step — see the changelog's D6a entry.
- **[`include/SushiDSP/math/dk/`](../include/SushiDSP/math/dk/)** — the DK-method circuit core:
  `DenseLu` (fixed-size LU), `DampedNewtonSolver`, `DkNetlist` (the control-thread netlist
  builder) and `DkCircuit<S, N, I, O>` (trapezoidal discretisation and the per-sample solve).
  Header-only, standard library only, and it never names a circuit model — the models arrive as a
  template parameter. Design spec §4.5, "As built in D6b".
- **[`include/SushiDSP/math/Resampler.hpp`](../include/SushiDSP/math/Resampler.hpp)** — the
  arbitrary-ratio polyphase resampler, for a conversion ratio that moves while audio runs (the
  DD-3's clock is the first consumer). One fractional phase accumulator walks the prototype in
  `ResamplerCoefficients.hpp`, generated by `tools/dsp/design_resampler.py`; a rate change moves
  the accumulator's step and never rebuilds a bank. `latency_seconds()` reports availability
  look-ahead, `34 / min(source, target)`; the converter is zero phase, so output time *t* carries
  input time *t* and subtracting the number as an alignment offset is wrong. Design spec §4.4.
- **[`include/SushiDSP/circuits/models/`](../include/SushiDSP/circuits/models/)** — the device
  laws the solver calls back into: `SiliconDiode`, `Triode12AX7`, `PentodeEL34`, and the shared
  `SoftTransition` softplus/logistic helpers. Each exposes `current` and `jacobian` in `double`
  against its `.sub` file's exact constants, and is C¹ everywhere.
- **[`modules/tubescreamer/`](../modules/tubescreamer/)** — the Ibanez Tube Screamer,
  `sushidsp.tubescreamer`, the D3 product that validated the shared DK solver core before
  JCM800. Its [`README.md`](../modules/tubescreamer/README.md) says which class owns which
  block and the one known deviation from the design spec's oversampling figure.
- **[`modules/routing/`](../modules/routing/)** — the rig graph's own routing nodes
  (`SplitterNode`, `MixerNode`, `PanNode`), `sushidsp.splitter`/`sushidsp.mixer`/`sushidsp.pan`.
  Its [`README.md`](../modules/routing/README.md) says why they exist as ordinary nodes rather
  than `RigGraph` special cases.
- **[`modules/cabinet/`](../modules/cabinet/)** — the standalone cabinet impulse-response node,
  `sushidsp.cabinet`. Its [`README.md`](../modules/cabinet/README.md) says why it replaced the
  amp-embedded `ICabinetHost` path that `modules/jcm800`, `modules/peavey5150`,
  `modules/diezel_vh4` and `modules/mesa_mark2c` used to implement.
- **[`modules/node_registry/`](../modules/node_registry/)** — the product catalog:
  `node_registry()` and `make_node()`, the one place in the tree allowed to depend on every
  product module at once. Its [`README.md`](../modules/node_registry/README.md) lists what is
  registered today.
- **[`modules/rig_preset/`](../modules/rig_preset/)** — portable rig presets as JSON,
  `serialize_rig_to_json()`/`deserialize_rig_from_json()`. Its
  [`README.md`](../modules/rig_preset/README.md) says how a product-specific host extends the
  schema without this module knowing about it.
- **[`modules/dd3/`](../modules/dd3/)** — the Boss DD-3 delay, `sushidsp.dd3`. Its
  [`README.md`](../modules/dd3/README.md) says which revision is modelled, which class owns which
  block, the three constants that are calibrations rather than component values, and what is left
  out; the spec is
  [`docs/superpowers/specs/2026-09-05-dd3-spx90-design.md`](superpowers/specs/2026-09-05-dd3-spx90-design.md).
- **[`modules/peavey5150/`](../modules/peavey5150/)**,
  **[`modules/mesa_mark2c/`](../modules/mesa_mark2c/)** and
  **[`modules/diezel_vh4/`](../modules/diezel_vh4/)** — the three high-gain amplifiers sibling to
  the JCM800 (design spec §5a). Each module's own README says where its model departs from its
  design dossier under `docs/reference/research/`.
- **[`modules/capture/`](../modules/capture/)** — recording and playing takes back, the DS phase's
  own module: no circuit, no `NodeDescriptor`, only the core as a dependency. Its
  [`README.md`](../modules/capture/README.md) says which class owns what, which of its three
  functions the audio thread calls, how the processed/dry pair stays sample-aligned and how a take
  is published to a playing track; the spec is
  [`docs/superpowers/specs/2026-09-07-stereo-tracks-design.md`](superpowers/specs/2026-09-07-stereo-tracks-design.md)
  and the design section is `docs/design/sushidsp.md` §3a.
- **[`modules/room/`](../modules/room/)** — one cabinet in one room, `sushidsp.room`: a shoebox
  solved on the control thread, its direct sound, early reflections, standing waves and late tail
  rendered on the audio thread, for two ears or one microphone. Its
  [`README.md`](../modules/room/README.md) says which class owns which block, which of them the
  audio thread calls, how a publish crossfades, and every approximation named as such; the spec is
  [`docs/superpowers/specs/2026-09-08-room-acoustics-design.md`](superpowers/specs/2026-09-08-room-acoustics-design.md),
  the plan
  [`docs/superpowers/plans/2026-09-08-room-acoustics.md`](superpowers/plans/2026-09-08-room-acoustics.md),
  and the design section is `docs/design/sushidsp.md` §3c.
- **[`assets/hrtf/`](../assets/hrtf/)** — where the room looks for its head-related transfer
  function. Its [`README.md`](../assets/hrtf/README.md) states the byte layout, the licence a
  bundled set must carry and how to regenerate the file with `tools/dsp/convert_hrtf.py`. No
  measured set is in the repository, so every rig runs `SphericalHeadHrtf` instead; same spec and
  plan as `modules/room/`.
- **[`tools/`](../tools/)** — developer-side scripts that are not part of the shipped library:
  `tools/dsp/design_halfband.py` (regenerates `include/SushiDSP/math/HalfbandCoefficients.hpp`
  from a scipy `remez` design), `tools/dsp/design_resampler.py` (regenerates
  `include/SushiDSP/math/ResamplerCoefficients.hpp` from a Kaiser-windowed sinc, and fails if the
  design stops clearing −100 dB) and `tools/spice/export.py` (runs the SPICE corpus above through
  LTspice and exports its output to CSV).
- **[`tests/measure/`](../tests/measure/)** — the test-side measurement library (`render`,
  `thd`, `alias_floor`, `frequency_response`, `null_test`) every product's plausibility and
  alias-floor test is built on.
- **[`tests/circuits/`](../tests/circuits/)** — test-side circuit descriptions shared across the
  unit tests and the benchmark, so the same block is not transcribed twice. Currently
  `JcmV1aNetlist.hpp`, the JCM800 V1a stage as a `DkNetlist`.

## Generated API reference

`sd doxygen` builds `docs/api-site/html/` from the headers under `include/SushiDSP/`, starting
from [`docs/api/mainpage.md`](api/mainpage.md). It documents what the headers say; it is not a
substitute for the design spec's reasoning.

## Implementation record

`docs/superpowers/plans/` holds the implementation plan for each roadmap phase (D0, D1, D2, …),
each with a `- [ ]` checklist of TDD steps. They are historical execution records once a phase
merges — later phases may use different tooling or conventions, and an old plan is not updated
to match; read the design spec for the current state, not an old plan.
