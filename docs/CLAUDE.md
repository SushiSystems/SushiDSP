# CLAUDE.md

## Getting oriented

When starting work on this project:

1. Follow the Sushi Systems doctrine (`sushisystemsprogramming`) and repository conventions.
2. Read `docs/CONTRIBUTING.md` first and follow its rules exactly.
3. Then read `docs/README.md`, the manual's index, and follow it into what your task touches.
4. `docs/design/sushidsp.md` is the design spec — it records intent, so it may describe work
   that does not exist yet; read it before changing the subsystem it covers, and never treat it
   as a description of the tree as it stands. `docs/api-site/` (once generated by `sd doxygen`)
   is Doxygen output — never edit it by hand.

## How to work

Act as an expert in whatever role the task requires, and work with real engineering discipline —
not a quick hack that happens to pass. All work complies with the Sushi Systems doctrine
(`sushisystemsprogramming`): one discipline across every repository, maintainability first, and
SOLID without exception.

### Priority 1: Maintainability

Everything must be SOLID and heavily encapsulated within its own boundaries. Every module should
be so well-isolated that:

- Changes stay local instead of rippling across the codebase.
- Anything can be found quickly by someone looking for it.

This is the single biggest determinant of the project's long-term fate, which is why it comes
before everything else — including performance.

### Priority 2: Performance

The DSP core runs on the real-time audio thread. `IAudioNode::process()` — and everything called
from it — must be allocation-free, lock-free, syscall-free, and throw-free; that bar is enforced
by RT-safety trap tests, not left to review. Outside the real-time path, treat wasted cycles as a
real cost: "engineer it once carefully, run it a thousand times cheaply."

### Quality bar

Hold an extremely high, borderline obsessive standard of quality and correctness. Sloppy or
"good enough for now" work is not acceptable — especially in the circuit/solver math, where a
plausible-looking but wrong equation produces audio that sounds fine until it doesn't.

### Honesty

Always be honest, never lie. Mutual honesty between us is what lets us actually make progress.

If a task turns out to be too large to finish, never quietly cut corners and claim it's done, or
claim things were done that were not. Say plainly what was completed and what wasn't. When a
design decision deliberately narrows scope (e.g. deferring the WDF adaptor tree until a real
circuit needs it), say so explicitly in the plan/spec rather than silently under-delivering.

If a task requires making a choice, ask the user rather than picking arbitrarily out of laziness
— laziness in place of asking is never acceptable.

### Building

Never invoke the underlying build system (cmake, ctest) directly. All builds and program actions
must go through this project's `sd` command line tool — `sd build`, `sd test`, `sd doxygen`. Learn
and use the CLI; it is not optional.

### Task tracking

For every implementation, create tasks up front and diligently update the task list as work
progresses. Manage the project's implementation carefully through that to-do list, not from
memory.
